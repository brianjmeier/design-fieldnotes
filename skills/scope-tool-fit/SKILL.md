# Choose scope and tools by the outcome

## Mental model

Tools, project scope, and pricing discussions are contextual. Their useful lesson is to understand the work and its intended value before choosing an execution path. A dated resource list is not a current recommendation.

## When this skill applies

Use when briefing design work, choosing a tool, or estimating an agent’s implementation scope.

## Reasoning

Describe the deliverable concretely: pages, states, interactions, content, evidence, and handoff format. Distinguish a visual concept from production behavior. Choose the smallest available tool set that can demonstrate the intended outcome.

Record assumptions that affect effort, including content readiness, responsive behavior, integrations, and review. Verify current tool capabilities from official documentation when needed. Historical price examples should not become a fixed quote or universal rate.

## Worked example — original implementation adaptation

A dashboard request

Before: “Build a dashboard” leaves unclear whether the work includes live data, errors, filtering, authentication, or just a visual model.

After: the brief names the decision, sample data, implemented states, responsive scope, and verification evidence. Tool choice follows those requirements.

## Failure modes

- Treating sponsor claims as neutral capability evidence.

- Using a historical price example as current market guidance.

- Installing tools or purchasing services without authorization.

## Evidence that would support the decision

A reviewer can map each promised deliverable to an implementation and its evidence. Assumptions and exclusions are explicit.
