# Transfer the mechanism from a reference

## Mental model

References are most useful when they explain a design decision. A pattern’s task, context, and behavior matter more than its superficial appearance. Combining unrelated references still requires a coherent system.

## When this skill applies

Use when starting a layout, exploring alternatives, or specifying work for a coding agent.

## Reasoning

For each reference, state the problem it solves and the part worth borrowing: navigation hierarchy, section sequence, information density, or interaction feedback. Examine the active flow, not only an isolated image.

Adapt to your real content and constraints. Keep the project’s own tokens and components when they fit. Reject patterns whose assumptions differ, and show the intended before/after when briefing another agent.

## Worked example — original implementation adaptation

Briefing an agent on a support queue

Before: “Make this look like a premium SaaS dashboard” leaves the agent to invent the structure.

After: the brief specifies a comparison table from one reference, contextual detail from another, and the existing product’s controls. Each reference has a reason and a stated limit.

## Failure modes

- Borrowing appearance without the behavior that makes it useful.

- A collage of different visual systems.

- Reusing proprietary assets without permission.

## Evidence that would support the decision

Explain the borrowed mechanism and test it with your own content. Compare the resulting task flow against the reference assumption you intended to preserve.
